## 1. 主な設計判断

要件定義で決めていない点のうち、実装の形に大きく効くものを示す。変更したい場合は指摘してほしい。

| ID | 判断 | 理由 | 主な代替案 |
| --- | --- | --- | --- |
| D1 | `Viewer` をロールごとの型（sealed interface）に分ける | 依頼者に許されない操作を呼ぶコードがコンパイルエラーになる。`switch` の網羅性検査で、可視性条件の書き漏れも検出できる。 | ロールを列挙型の項目に持つ単一の `record Viewer`（判定が実行時になる） |
| D2 | バックエンドは機能単位のパッケージ（package-by-feature）＋各機能内の 4 層 | チケット、ビュー、通知などの変更が 1 つのパッケージで閉じる。ArchUnit で依存方向を検査できる。 | 技術層ごとのパッケージ（controller / service / repository） |
| D3 | 依頼者向け API を `/portal/...` に分け、別の DTO を返す | 内部項目（担当グループ、タグ、監査ログ）を依頼者向けの応答に入れる余地を作らない。 | 同じ API で、ロールに応じて項目を出し分ける |
| D4 | 担当者とグループの整合性、ステータスと担当者の関係を DB の制約でも保証する | ドメイン層の誤りがデータを壊さない。 | アプリケーションの検査だけ |
| D5 | 監査ログとコメントの追記のみを、DB ロールの権限（UPDATE / DELETE を与えない）でも保証する | F-L-2、F-C-2 をコード以外でも証明できる。 | アプリケーションに更新・削除の手段を作らないだけ |
| D6 | 通知は Transactional Outbox で送る | チケットの更新とメール送信の整合が取れる。SMTP の障害で更新が失敗しない。 | 更新後に同期で送信、または `@TransactionalEventListener` で非同期送信 |
| D7 | 楽観ロック（`version`）で同時編集を検出する | エージェント同士の上書きを防ぐ。 | 最後の更新が勝つ |
| D8 | 1 つの SPA にエージェント画面とポータルを入れる | 部品と配信を共有できる。領域ごとに遅延読み込みする。 | エージェント用とポータル用に 2 つのアプリ |
| D9 | サーバーの状態は TanStack Query、UI 部品は PrimeVue | 取得・再取得・エラー処理と、表・選択部品を自前で書かずに済む。 | Pinia だけで管理、UI 部品は自作または他のライブラリ |
| D10 | 添付はローカルファイル（Docker ボリューム）に保存し、`BlobStore` で抽象化する | 1 コマンド起動（N-7）に追加のサービスが要らない。 | MinIO（S3 互換）を compose に追加 |

## 2. 要件定義書からの変更点

設計の過程で、要件定義書 6 章のデータモデル概要から次の点を変えた。要件定義書 v0.4 に反映済み。

- `Group` 表の名前を `agent_groups` にした（`group` は SQL の予約語）。
- `View.shared` 列をやめ、`owner_id IS NULL` を共有ビューとした（2 列の矛盾を防ぐ）。
- `Ticket` に `version`（楽観ロック）と `follow_up_of`（クローズ後の返信で起票したチケットの元）を加えた。
- `TicketEvent` に `change_id`（1 回の更新をまとめる）を加え、値を `jsonb` にした。
- 添付に `uploader_id` を加え、コメントに紐付く前の状態（`comment_id IS NULL`）を許した。
- `user_tokens`（招待・メール確認・パスワード再設定）と `notification_outbox` を加えた。

## 3. 次の段階

この設計に合意したら、次の順で実装する。各段階を 1 つ以上のプルリクエストにする。

1. 骨組み: `docker compose`、Maven と Vite のプロジェクト、CI、Flyway の初期マイグレーション、`Viewer` と可視性条件、ArchUnit
2. テナント・認証: サインアップ、ログイン、招待、依頼者登録
3. チケット: 作成・詳細・更新、ステータス遷移、コメント、監査ログ
4. ビュー・検索
5. 通知、自動クローズ
6. ポータル
7. 管理画面、添付、一括更新
8. デモデータ、E2E（受け入れ基準 1〜13）、README
