# 要件定義書（ドラフト）

- 対象: like-zendesk（Zendesk ライクなインシデント／チケット管理システム）
- 版: v0.1（2026-10-17）
- 状態: ドラフト。「10. 未決事項」の回答を受けて v0.2 で確定する。

本書では、未決事項について仮の前提（**[仮]** と表記）を置いて書いている。未決事項の回答で前提が変わった場合は、該当箇所を書き換える。

## 1. 目的

問い合わせやインシデントをチケットとして一元管理し、次の状態を実現する。

- 依頼者からの問い合わせを取りこぼさない。
- 誰が、どのチケットを、どの状態で持っているかが常にわかる。
- 依頼者とのやり取りと社内の検討（社内メモ）を、チケット単位で履歴として残す。
- 対応の遅れ（SLA 違反の恐れ）に早く気づける。

## 2. スコープ

### 2.1 前提 [仮]

- 用途: 社外の顧客からの問い合わせ対応（カスタマーサポート）。社内ヘルプデスクにも流用できる汎用設計にする。
- 提供形態: 単一組織向け（シングルテナント）。SaaS としての多テナント対応はしない。
- 言語: UI は日本語のみ。
- 規模: エージェント 50 人以下、チケット 年間 10 万件以下。

### 2.2 MVP に含めるもの

| ID | 範囲 |
| --- | --- |
| S-1 | チケットの作成・閲覧・更新（エージェント用 Web 画面） |
| S-2 | ステータス、優先度、種別、担当者、担当グループの管理 |
| S-3 | 公開コメントと社内メモ |
| S-4 | 依頼者用ポータル（チケットの起票、自分のチケットの閲覧、返信） |
| S-5 | ビュー（保存済みフィルタ）と全文検索 |
| S-6 | メール通知（チケット作成時、公開コメント追加時、ステータス変更時） |
| S-7 | ユーザー・グループ・ロールの管理 |
| S-8 | 監査ログ（チケットの変更履歴） |

### 2.3 MVP に含めないもの（将来検討）

- メール受信によるチケット自動起票（[仮] MVP 直後の第 2 段階で対応）
- マクロ（定型返信と一括更新）
- トリガー・オートメーション（条件に応じた自動処理）
- SLA ポリシーと違反アラート
- ナレッジベース（ヘルプセンター）
- チャット、電話、SNS などのチャネル
- 満足度調査（CSAT）
- レポート・ダッシュボード
- 外部連携 API、Webhook
- 多言語対応、多テナント対応

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| チケット | 1 件の問い合わせまたはインシデント。対応の単位。 |
| 依頼者（Requester） | チケットを起票した人。社外の顧客を想定。 |
| エージェント（Agent） | チケットに対応する担当者。 |
| グループ | エージェントの集まり（例: 一次対応、インフラ、請求）。 |
| 公開コメント | 依頼者に見えるコメント。 |
| 社内メモ | エージェントだけに見えるコメント。 |
| ビュー | 保存済みの検索条件。チケット一覧として表示する。 |

## 4. ロールと権限

| ロール | できること |
| --- | --- |
| 依頼者 | 自分のチケットの起票・閲覧・公開コメント追加。他人のチケットと社内メモは見えない。 |
| エージェント | すべてのチケットの閲覧・更新・コメント（公開／社内）。自分用ビューの作成。 |
| 管理者 | エージェントの権限に加え、ユーザー・グループ・ロール・共有ビュー・項目設定の管理。 |

[仮] エージェントは所属グループに関係なく全チケットを閲覧できる。グループ単位で閲覧を制限するかは未決事項 Q5。

## 5. 機能要件

優先度: **Must** = MVP 必須、**Should** = MVP に入れたい、**Could** = 余裕があれば。

### 5.1 チケット

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-T-1 | エージェントは、依頼者を指定してチケットを作成できる。 | Must |
| F-T-2 | チケットは次の項目を持つ: 番号（連番）、件名、本文、依頼者、ステータス、優先度、種別、担当グループ、担当者、タグ、作成日時、更新日時。 | Must |
| F-T-3 | 優先度は 低 / 通常 / 高 / 緊急 の 4 段階とする。 | Must |
| F-T-4 | 種別は 質問 / インシデント / 問題 / タスク の 4 種とする。 | Must |
| F-T-5 | ステータスは「7. ステータス遷移」に従う。 | Must |
| F-T-6 | エージェントは、担当者と担当グループを変更できる。担当者を設定するときは、その担当者が属するグループだけを選べる。 | Must |
| F-T-7 | チケットにファイルを添付できる（1 ファイル 20MB まで）。 | Should |
| F-T-8 | 複数チケットをまとめて更新できる（ステータス、担当者、タグ）。 | Should |
| F-T-9 | 重複チケットを別チケットに統合できる。 | Could |
| F-T-10 | 種別が「インシデント」のチケットを「問題」チケットに紐付けられる。問題を解決すると、紐付いたインシデントも解決にできる。 | Could |

### 5.2 コメント

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-C-1 | エージェントは、公開コメントと社内メモを追加できる。画面上で両者を明確に区別して表示する。 | Must |
| F-C-2 | コメントは追記のみとし、編集・削除はできない。 | Must |
| F-C-3 | コメント追加と同時にステータス等を更新できる（例: 返信して「保留」にする）。 | Must |
| F-C-4 | コメント本文は Markdown またはリッチテキストで書ける。 | Should |

### 5.3 依頼者ポータル

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-P-1 | 依頼者は、Web フォームからチケットを起票できる（件名、本文、添付）。 | Must |
| F-P-2 | 依頼者は、自分のチケットの一覧と詳細（公開コメントのみ）を見られる。 | Must |
| F-P-3 | 依頼者は、自分のチケットに返信できる。「解決済み」のチケットに返信すると「オープン」に戻る。 | Must |
| F-P-4 | 依頼者は、自分のチケットを「解決済み」にできる。 | Should |

### 5.4 一覧・ビュー・検索

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-V-1 | 標準ビューを用意する: 自分の未解決チケット、未割り当てチケット、自グループの未解決チケット、最近更新されたチケット。 | Must |
| F-V-2 | エージェントは、条件（ステータス、優先度、種別、担当者、グループ、タグ、作成日・更新日）を組み合わせて個人ビューを作れる。管理者は共有ビューを作れる。 | Must |
| F-V-3 | 一覧は任意の列で並べ替えられる。 | Must |
| F-V-4 | 件名・本文・コメントを対象に全文検索できる（日本語対応）。 | Must |
| F-V-5 | ビューごとの件数を表示する。 | Should |

### 5.5 通知

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-N-1 | チケット作成時、依頼者に受付メールを送る。 | Must |
| F-N-2 | 公開コメント追加時、依頼者（エージェントが書いた場合）または担当者（依頼者が書いた場合）にメールを送る。 | Must |
| F-N-3 | 担当者に割り当てられたとき、その担当者に通知する。 | Must |
| F-N-4 | 画面内通知（未読バッジ）。 | Could |

### 5.6 メール受信（第 2 段階 [仮]）

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-M-1 | 指定アドレス宛のメールからチケットを起票する。送信者を依頼者として登録する。 | Should |
| F-M-2 | 通知メールへの返信を、元チケットの公開コメントとして取り込む。 | Should |

### 5.7 ユーザー・管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-A-1 | 管理者は、エージェントを招待・無効化できる。 | Must |
| F-A-2 | 依頼者はポータルで自己登録できる（メールアドレス確認あり）。 | Must |
| F-A-3 | 管理者は、グループを作成し、エージェントを所属させられる（複数所属可）。 | Must |
| F-A-4 | 管理者は、タグの候補とチケットのカスタム項目を定義できる。 | Could |

### 5.8 監査

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-L-1 | チケットの全項目変更を「誰が・いつ・何を・何から何に」の形で記録し、チケット画面で時系列表示する。 | Must |
| F-L-2 | 監査ログは画面から編集・削除できない。 | Must |

## 6. データモデル概要

```
User(id, name, email, role: requester|agent|admin, active)
Group(id, name)
GroupMembership(user_id, group_id)
Ticket(id, number, subject, requester_id, status, priority, type,
       group_id?, assignee_id?, tags[], created_at, updated_at, solved_at?, closed_at?)
Comment(id, ticket_id, author_id, body, public: bool, created_at)
Attachment(id, comment_id, filename, size, storage_key)
TicketEvent(id, ticket_id, actor_id, field, from, to, created_at)   -- 監査ログ
View(id, owner_id?, name, conditions, sort, shared: bool)
```

- `assignee_id` があれば、その担当者は `group_id` のグループに属していること（F-T-6）。
- チケットの本文は最初の公開コメントとして保存する（Zendesk と同じ扱い）。

## 7. ステータス遷移

Zendesk の標準ステータスに合わせる。

| ステータス | 意味 |
| --- | --- |
| 新規（New） | 起票直後。担当者が未設定。 |
| オープン（Open） | 担当者がつき、エージェント側の対応待ち。 |
| 保留（Pending） | 依頼者の返答待ち。 |
| 待機（On-hold） | 第三者（社内他部署、ベンダー）の対応待ち。 |
| 解決済み（Solved） | 対応完了。依頼者の返信で再オープンできる。 |
| クローズ（Closed） | 確定。変更不可。 |

```
新規 → オープン / 保留 / 待機 / 解決済み
オープン ⇄ 保留 ⇄ 待機（相互に遷移可）
オープン / 保留 / 待機 → 解決済み
解決済み → オープン（依頼者の返信、またはエージェントの再オープン）
解決済み → クローズ（解決から 4 日後に自動）
クローズ → （遷移なし。依頼者の返信は新しいチケットとして起票し、元チケットへのリンクを付ける）
```

- 「新規」のチケットに担当者を設定し、他のステータスを指定しなければ、自動で「オープン」になる。
- 担当者が設定されたチケットは「新規」に戻らない。
- 「解決済み」にするには担当者が必要。

| ID | 区分 | 要件 |

| N-2 | 性能 | 全文検索は 2 秒以内（95 パーセンタイル）。 |
| N-3 | セキュリティ | 認証はメールアドレスとパスワード。パスワードはハッシュ化して保存する。SSO は将来検討。 |

| N-5 | セキュリティ | 通信は HTTPS のみ。OWASP Top 10 の対策を行う。 |

## 9. 受け入れ基準（MVP 完了の判定）

次のシナリオがすべて画面操作で通れば、MVP 完了とする。

1. 依頼者がポータルで自己登録し、チケットを起票する。依頼者に受付メールが届く。
2. エージェントが「未割り当て」ビューでそのチケットを見つけ、自分を担当者にする。ステータスが「オープン」になる。
3. エージェントが社内メモを書く。依頼者のポータルにはそのメモが表示されない。
4. エージェントが公開コメントで質問し、ステータスを「保留」にする。依頼者にメールが届く。
5. 依頼者がポータルで返信する。ステータスが「オープン」に戻り、担当者にメールが届く。
6. エージェントが「解決済み」にする。4 日後に「クローズ」になる。クローズ後は項目を変更できない。
7. チケット画面に、1〜6 の変更がすべて監査ログとして時系列で表示される。
8. 別の依頼者は、このチケットを URL 直打ちでも API でも閲覧できない。
9. エージェントが件名の一部（日本語）で検索し、このチケットが見つかる。
