# 要件定義書

- 対象: like-zendesk（Zendesk ライクなインシデント／チケット管理システム）
- 版: v0.4（2026-10-18）
- 状態: スコープ確定。「10. 決定事項」の内容を反映済み。「11. 残りの論点」は既定値で進め、異論があれば変更する。6 章のデータモデルは設計（[docs/design/](design/README.md)）に合わせて更新済み。

## 1. 目的

問い合わせやインシデントをチケットとして一元管理する、多テナント型の Web サービスを作る。本プロジェクトはポートフォリオとして公開することを目的とする。

サービスとして、次の状態を実現する。

- 依頼者からの問い合わせを取りこぼさない。
- 誰が、どのチケットを、どの状態で持っているかが常にわかる。
- 依頼者とのやり取りと社内の検討（社内メモ）を、チケット単位で履歴として残す。
- 複数のテナント（サービスを契約する単位）が 1 つのサービスを使い、互いのデータが一切見えない。

ポートフォリオとして、次の点を見せられる状態にする。

- テナント分離、権限制御、状態遷移を、設計と自動テストで保証していること。
- リポジトリを clone して 1 コマンドで起動し、デモデータで全機能を試せること。

## 2. スコープ

### 2.1 前提

- 用途: 社外の顧客サポートと社内 IT ヘルプデスクの両方に使える。テナントごとに依頼者の登録方法を切り替える（F-A-2）。
- 提供形態: 多テナント SaaS。1 つのデプロイで複数テナントを収容する。課金は扱わない。
- 言語: UI は日本語のみ。
- 規模の想定: テナント 10、テナントあたりエージェント 50 人以下、チケット 10 万件以下。性能確認はこの規模のデモデータで行う。

### 2.2 MVP に含めるもの

| ID | 範囲 |
| --- | --- |
| S-1 | テナントの作成（サインアップ）とテナント分離 |
| S-2 | チケットの作成・閲覧・更新（エージェント用 Web 画面） |
| S-3 | ステータス、優先度、種別、担当者、担当グループの管理 |
| S-4 | 公開コメントと社内メモ |
| S-5 | 依頼者用ポータル（チケットの起票、自分のチケットの閲覧、返信） |
| S-6 | ビュー（保存済みフィルタ）と全文検索 |
| S-7 | メール通知（チケット作成時、公開コメント追加時、割り当て時） |
| S-8 | ユーザー・グループ・ロールの管理 |
| S-9 | 監査ログ（チケットの変更履歴） |
| S-10 | デモデータ投入と API ドキュメント（OpenAPI） |

### 2.3 MVP に含めないもの（将来検討）

- メール受信によるチケット自動起票（MVP 直後の第 2 段階で対応）
- SLA ポリシーと違反アラート
- マクロ（定型返信と一括更新）
- トリガー・オートメーション（条件に応じた自動処理）
- ナレッジベース（ヘルプセンター）
- チャット、電話、SNS などのチャネル
- 満足度調査（CSAT）
- レポート・ダッシュボード
- 外部連携用の公開 API キー、Webhook
- SSO（SAML / OIDC）
- 課金、プラン管理
- 多言語対応

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| テナント | サービスの契約単位。データはテナント単位で完全に分離する。「組織」とは呼ばない。 |
| 所属組織（Organization） | 依頼者の所属先（取引先の会社名、社内の部署名）。管理者が設定し、チケット一覧の絞り込みに使う。テナントの内側にある。 |
| チケット | 1 件の問い合わせまたはインシデント。対応の単位。 |
| 依頼者（Requester） | チケットを起票した人。社外の顧客、または社内の従業員。 |
| エージェント（Agent） | チケットに対応する担当者。 |
| 管理者（Admin） | ユーザー・グループ・共有ビュー・テナント設定も管理するエージェント。エージェントとして数える。 |
| グループ | エージェントの集まり（例: 一次対応、インフラ、請求）。 |
| 公開コメント | 依頼者に見えるコメント。 |
| 社内メモ | エージェントだけに見えるコメント。 |
| ビュー | 保存済みの検索条件。チケット一覧として表示する。 |

## 4. ロールと権限

ロールはテナント内で定義する。どのロールも、自分のテナント以外のデータには一切アクセスできない。

| ロール | できること |
| --- | --- |
| 依頼者 | 自分のチケットの起票・閲覧・公開コメント追加。他人のチケットと社内メモは見えない。 |
| エージェント | テナント内のすべてのチケットの閲覧・更新・コメント（公開／社内）。自分用ビューの作成。 |
| 管理者 | エージェントの権限に加え、ユーザー・グループ・共有ビュー・テナント設定の管理。 |

エージェントは、所属グループに関係なくテナント内の全チケットを閲覧できる。

## 6. データモデル概要

```
Tenant(id, slug, name, requester_signup: open|domain_restricted, allowed_domains[], next_ticket_number, created_at)
User(id, tenant_id, name, email, role: requester|agent|admin, organization_id?, active)
Organization(id, tenant_id, name)                         -- 依頼者の所属組織 (F-A-4)
AgentGroup(id, tenant_id, name)                           -- テーブル名 agent_groups（group は予約語）
GroupMembership(tenant_id, user_id, group_id)
Ticket(id, tenant_id, number, subject, requester_id, status, priority, type,
       group_id?, assignee_id?, tags[], follow_up_of?, version, created_at, updated_at, solved_at?, closed_at?)
Comment(id, tenant_id, ticket_id, author_id, body, public: bool, created_at)
Attachment(id, tenant_id, comment_id?, uploader_id, filename, content_type, size, storage_key)
TicketEvent(id, tenant_id, ticket_id, change_id, actor_id?, field, from, to, created_at)   -- 監査ログ
View(id, tenant_id, owner_id?, name, conditions, sort)    -- owner_id が NULL なら共有ビュー
UserToken(id, tenant_id, user_id, purpose, token_hash, expires_at, used_at?)            -- 招待・メール確認・パスワード再設定
NotificationOutbox(id, tenant_id, kind, recipient_id, payload, state, attempts, ...)   -- 通知メールの送信待ち
```

詳細なテーブル定義、制約、インデックスは [データモデル設計](design/data-model.md) を正とする。

- すべてのテーブルに `tenant_id` を持たせる。テナント分離と依頼者の閲覧制限は、SQL クエリの条件で制御する（「6.1 可視性制御」）。
- テナントをまたぐ参照を防ぐため、外部キーは `(tenant_id, id)` の複合キーで張る（例: `Ticket(tenant_id, assignee_id)` → `User(tenant_id, id)`）。
- 一意制約: `Tenant.slug` はサービス全体で一意。`User` の `(tenant_id, email)` と `Ticket` の `(tenant_id, number)` はテナント内で一意。
- `assignee_id` があれば、その担当者は `group_id` のグループに属していること（F-T-6）。
- チケットの本文は最初の公開コメントとして保存する（Zendesk と同じ扱い）。

### 6.1 可視性制御

PostgreSQL の行レベルセキュリティ（RLS）は使わない。誰に何が見えるかは、アプリケーションが発行する SQL の WHERE 句で決める。

- リクエストごとに、認証情報から「閲覧者」（`Viewer`: テナント ID、ユーザー ID、ロール）を作る。テナント ID は URL のテナント識別子とログインユーザーの所属が一致した場合だけ確定し、一致しなければ 404 を返す。
- テナントのデータを読み書きするリポジトリのメソッドは、すべて `Viewer` を必須の引数に取る。`Viewer` なしでテナントのデータを取得する手段を用意しない。
- 可視性の条件は、エンティティごとに 1 か所（可視性条件を組み立てる関数）で定義し、各クエリはそれを WHERE 句に結合する。

| 対象 | エージェント・管理者 | 依頼者 |
| --- | --- | --- |
| チケット | `tenant_id = :viewer_tenant` | `tenant_id = :viewer_tenant AND requester_id = :viewer_user` |
| コメント | `tenant_id = :viewer_tenant` | 上記のチケット条件 `AND public = true` |
| 添付 | 親コメントの条件に従う | 親コメントの条件に従う |
| 監査ログ | `tenant_id = :viewer_tenant` | 閲覧不可 |
| ユーザー・グループ・ビュー | `tenant_id = :viewer_tenant` | 自分自身のみ |

- 更新・削除の SQL にも同じ条件を付け、更新件数が 0 件なら 404 とする。他テナントの ID を指定されても、存在しない場合と区別できない応答を返す。
- 次の 3 つで条件漏れを検出する。(1) 可視性条件を組み立てる関数の単体テスト。(2) 全 API エンドポイントについて、他テナント・他依頼者の ID を指定して 404 になることを確かめる結合テスト。(3) リポジトリ層の公開メソッドが `Viewer` を引数に取ることを検査するアーキテクチャテスト（ArchUnit）。

## 7. ステータス遷移

Zendesk の標準ステータスに合わせる。

| ステータス | 意味 |
| --- | --- |
| 新規（New） | 起票直後。担当者が未設定。 |
| オープン（Open） | 担当者がつき、エージェント側の対応待ち。 |
| 保留（Pending） | 依頼者の返答待ち。 |
| 待機（On-hold） | 第三者（社内他部署、ベンダー）の対応待ち。 |
| 解決済み（Solved） | 対応完了。依頼者の返信で再オープンできる。 |
| クローズ（Closed） | 確定。変更不可。 |

```
新規 → オープン / 保留 / 待機 / 解決済み
オープン ⇄ 保留 ⇄ 待機（相互に遷移可）
オープン / 保留 / 待機 → 解決済み
解決済み → オープン（依頼者の返信、またはエージェントの再オープン）
解決済み → クローズ（解決から 4 日後に自動）
クローズ → （遷移なし。依頼者の返信は新しいチケットとして起票し、元チケットへのリンクを付ける）
```

- 「新規」のチケットに担当者を設定し、他のステータスを指定しなければ、自動で「オープン」になる。
- 担当者が設定されたチケットは「新規」に戻らない。
- 「解決済み」にするには担当者が必要。
- 遷移規則はドメイン層の 1 か所で定義し、全遷移の組み合わせを単体テストで網羅する。

## 8. 非機能要件

ポートフォリオ用途のため、稼働率などの運用 SLA は定めない。代わりに、テナント分離・権限・品質を自動テストで証明することを重視する。

| ID | 区分 | 要件 |
| --- | --- | --- |
| N-1 | 性能 | チケット 10 万件のテナントで、チケット一覧・詳細の API 応答が 500ms 以内（ローカル環境、95 パーセンタイル）。 |
| N-2 | 性能 | 同条件で、全文検索の API 応答が 1 秒以内（95 パーセンタイル）。 |
| N-3 | セキュリティ | 認証はメールアドレスとパスワード。パスワードは bcrypt でハッシュ化する。セッションは HttpOnly Cookie で管理し、CSRF 対策を行う。 |
| N-4 | セキュリティ | テナント分離（F-X-3）と依頼者のアクセス制限（他人のチケット、社内メモ）を SQL の可視性条件（6.1）で強制し、結合テストで検証する。 |
| N-5 | セキュリティ | OWASP Top 10 の対策を行う。Markdown 表示時の XSS、添付ファイルのパス・種別を検証する。 |
| N-6 | 対応環境 | エージェント画面: 最新の Chrome / Edge / Safari / Firefox（PC）。ポータル: 加えてスマートフォンのブラウザ。 |
| N-7 | 開発環境 | `docker compose up` の 1 コマンドで、DB、API、フロントエンド、メール確認用サーバー（Mailpit）が起動する。 |
| N-8 | 品質 | GitHub Actions で、lint、型チェック、単体テスト、結合テスト、E2E テストをプルリクエストごとに実行する。 |
| N-9 | 品質 | 「9. 受け入れ基準」のシナリオを E2E テスト（Playwright）で自動検証する。 |
| N-10 | ドキュメント | README に、システム概要、アーキテクチャ図、起動手順、デモアカウント、設計上の判断（テナント分離方式など）を記載する。 |

## 9. 受け入れ基準（MVP 完了の判定）

次のシナリオがすべて画面操作で通れば、MVP 完了とする。

1. 利用者がサインアップ画面でテナント A を作成し、管理者としてログインする。
2. 管理者がエージェントを招待し、グループに所属させる。
3. 依頼者がテナント A のポータルで自己登録し、チケットを起票する。依頼者に受付メールが届く。
4. エージェントが「未割り当て」ビューでそのチケットを見つけ、自分を担当者にする。ステータスが「オープン」になる。
5. エージェントが社内メモを書く。依頼者のポータルにはそのメモが表示されない。
6. エージェントが公開コメントで質問し、ステータスを「保留」にする。依頼者にメールが届く。
7. 依頼者がポータルで返信する。ステータスが「オープン」に戻り、担当者にメールが届く。
8. エージェントが「解決済み」にする。4 日後（テストでは時刻を進めて確認）に「クローズ」になる。クローズ後は項目を変更できない。
9. チケット画面に、4〜8 の変更がすべて監査ログとして時系列で表示される。
10. 同じテナントの別の依頼者は、このチケットを URL 直打ちでも API でも閲覧できない。
11. テナント B の管理者・エージェントは、テナント A のチケットを URL 直打ちでも API でも閲覧できない。
12. テナント A の許可ドメインを設定すると（F-A-2 (b)）、許可外ドメインのアドレスでは依頼者登録できない。
13. エージェントが件名の一部（日本語）で検索し、このチケットが見つかる。

## 11. 残りの論点（既定値で進める）

次の点は既定値で設計を進める。変更したい場合は指摘してほしい。

| ID | 論点 | 既定値 | 理由 |
| --- | --- | --- | --- |
| R1 | テナントの URL 形式 | パス方式（`/t/{識別子}/...`） | ローカル環境とデモ環境でワイルドカード DNS や証明書が要らない。サブドメイン方式は後から追加できる。 |
| R2 | テナント分離の方式 | 共有スキーマ＋`tenant_id`＋SQL の可視性条件（RLS は使わない） | 2026-10-17 に決定。可視性のルールがアプリケーションのコードとテストに集まり、読んで確かめられる。 |
| R3 | 公開デモ環境 | MVP では用意しない（ローカル起動のみ） | デプロイ先は MVP 完成後に決める。 |
| R4 | テナント作成の制限 | 誰でも作成できる | ポートフォリオの閲覧者が自分で試せる。 |
| R5 | データアクセス方式 | Spring JDBC（`JdbcClient`）で SQL を手書きする | 可視性条件を SQL に明示するため。JPA の派生クエリは条件の付け忘れが見えにくい。jOOQ や MyBatis に変えてもよい。 |
